# Google ADK Go learning plan

This is a **handwrite** exercise. The learner writes the ADK agent code and
owns the design decisions. The assistant may explain APIs, suggest small
experiments, interpret compiler/runtime output, review a partial attempt, and
point to primary documentation. It must not replace the learner's agent with a
drop-in implementation.

The project is a **read-only field-research trip planner**. It researches
destinations, checks traveler constraints, remembers preferences, reads
reference documents, delegates research and fact-checking, and produces a
structured trip brief. It does not book travel, purchase anything, send
messages, or perform other side effects.

## Starting state

This directory is an isolated Go module because the selected ADK release
requires Go 1.26.10 or later while the repository's root Go module currently
declares Go 1.26.8. The nested module keeps that dependency and toolchain
decision local:

```text
/home/michael/src/github/language-practice/go/agents/adk/
├── go.mod       # prepared module; learner owns later dependency changes
├── go.sum       # generated by the learner's module commands
├── main.go      # compileable configuration scaffold, not an agent solution
└── PLAN.md      # this learning plan
```

The scaffold in `main.go` does only three things:

1. Reads `OPENROUTER_API_KEY`, `OPENROUTER_MODEL`, and optionally
   `OPENROUTER_BASE_URL`.
2. Constructs ADK's experimental OpenAI-compatible `model.LLM` adapter using
   OpenRouter's Chat Completions endpoint.
3. Prints configuration readiness without making a model request.

It deliberately does **not** construct an `llmagent`, runner, tool, session, or
workflow. Those are the learner's first implementation tasks below.

## Version and provider boundary

The plan targets Google ADK Go `v2.7.1`:

- ADK module: `google.golang.org/adk/v2`
- Go requirement: `1.26.10` or later
- OpenRouter adapter: `google.golang.org/adk/v2/model/openaimodel`
- OpenRouter endpoint: `https://openrouter.ai/api/v1`
- API selection: `openaimodel.APIChatCompletions`

OpenRouter is supported through ADK's experimental OpenAI-compatible adapter,
not through a dedicated OpenRouter package. Provider and model capabilities are
not uniform. Tool calling, structured output, streaming, multimodal input,
reasoning, and response formats must be tested with the specific model selected
by `OPENROUTER_MODEL`.

The adapter documentation states that `APIResponses` is its default, while
`APIChatCompletions` is the surface most OpenAI-compatible providers implement.
It also states that `BaseURL` points to an OpenAI-compatible provider. The
learning plan uses Chat Completions explicitly rather than relying on the zero
value.

## Environment and commands

Do not commit API keys. Run the scaffold from its module directory:

```bash
cd /home/michael/src/github/language-practice/go/agents/adk
export OPENROUTER_API_KEY='replace-with-your-key'
export OPENROUTER_MODEL='replace-with-a-model-id'
export OPENROUTER_BASE_URL='https://openrouter.ai/api/v1'

go run .
go build .
go vet ./...
```

The scaffold's successful output proves only that the local process read the
environment and constructed the ADK adapter. It does not prove network access,
authentication, model availability, billing permissions, inference success, or
tool compatibility.

When the learner reaches the first live model step, use a small prompt and
record the exact model ID, provider, API surface, date, and response/error. Live
requests may incur cost. Never paste an API key into source, a commit, or a
diagnostic transcript.

## Linear learning sequence

Complete each step in order. Before running a step, predict the observable
behavior. After running it, compare the prediction with the output, events,
errors, or traces. Keep the implementation small and commit learner-owned
checkpoints when the behavior is understood.

### 1. Inspect and verify the isolated module

**Concept:** Go modules, dependency boundaries, toolchain requirements, and
versioned import paths.

**Prerequisite:** Basic `go` command and module familiarity.

**Learner work:** Read `go.mod`, identify the nested module path, run the
scaffold, and explain why ADK uses `/v2` in every import.

```go

go 1.26.10

require google.golang.org/adk/v2 v2.7.1
```

Commands:

```bash
go version
go env GOTOOLCHAIN GOMOD GOPROXY
go mod tidy
go list -m all
go build .
```

**Validation:** `go build .` and `go vet ./...` pass from this directory.

**Reflection:** Which facts come from the module file, which come from the
host, and which remain unproven until a live request?

### 2. Understand the OpenRouter model adapter

**Concept:** Interface-based model selection and OpenAI-compatible endpoints.

**Learner work:** Explain the difference between `model.LLM`,
`openaimodel.ClientConfig`, and the provider endpoint. Run the scaffold with a
real key only after reviewing what it does and does not call.

```go
llm, err := openaimodel.NewModel(ctx, modelName, &openaimodel.ClientConfig{
	APIKey:  apiKey,
	BaseURL: "https://openrouter.ai/api/v1",
	API:     openaimodel.APIChatCompletions,
})
```

**Validation:** `llm.Name()` returns the selected OpenRouter model ID. Explain
why constructing the adapter does not establish inference connectivity.

**Failure modes:** Missing key, missing model, invalid API selection, a model
that does not support Chat Completions, or provider-specific request limits.

### 3. Construct the smallest LLM agent

**Concept:** Agent identity, model dependency, instructions, and explicit
errors.

**Learner work:** Add the `agent/llmagent` and `agent` imports to `main.go`,
construct one agent, and keep the configuration to four fields.

```go
root, err := llmagent.New(llmagent.Config{
	Name:        "trip_planner",

```

Do not add tools, sub-agents, callbacks, or schemas yet. The purpose is to see
the smallest useful boundary.

**Validation:** The agent has a non-empty name and can be passed to
`agent.NewSingleLoader`. Deliberately try an invalid configuration and record
the constructor error.

**Reflection:** Which behavior belongs to the model, which belongs to ADK, and
which belongs to the instruction text?

### 5. Add one deterministic, read-only function tool

**Concept:** Typed tool boundaries, generic functions, schema inference, and
error propagation.

**Learner work:** Write a local destination-facts tool backed by a small Go
map. It must never perform network I/O or side effects.

```go
type DestinationQuery struct {
	Destination string `json:"destination"`
}

lookup, err := functiontool.New(
	functiontool.Config{
		Name:        "lookup_destination",
		Description: "Returns local facts for a destination.",
	},
	func(ctx agent.Context, input DestinationQuery) (string, error) {
		// Learner writes lookup, normalization, and not-found behavior.
		return "", nil
	},
)
```

Add it to `llmagent.Config.Tools` only after testing the function directly.

**Validation:** Test a known destination, an unknown destination, empty input,
and a canceled context. Inspect the model's tool call and function response.

**Limits:** The OpenAI-compatible adapter documents that function tool
arguments are best effort and strict parameter validation is disabled. A
declared schema is not a substitute for validation inside the handler.

### 10. Understand sessions and events

**Concept:** A session is one conversation thread; events are its ordered
history; state is session-scoped key/value data.

**Learner work:** Create, retrieve, list, and delete an in-memory session.
Append an event manually and inspect it without contacting a model.

```go
created, err := service.Create(ctx, &session.CreateRequest{
	AppName:   "trip_planner",
	UserID:    "traveler-1",
	SessionID: "session-1",
})

event := session.NewEvent(ctx, "invocation-1")
event.Author = "user"
```

Iterate `created.Session.Events().All()` and compare `Len()` with the number of
events observed.

**Validation:** Test a missing session with `errors.Is(err, session.ErrNotFound)`
and distinguish it from malformed input or storage errors.

Sources:

- [Sessions and conversational context](https://google.github.io/adk-docs/sessions/)

### 11. Store traveler preferences in session state

**Concept:** Mutable state deltas and context visibility.

**Learner work:** Store budget, preferred pace, mobility needs, and home airport
in state. Read the state from a later tool invocation. Keep user-owned values
separate from framework metadata.

```go
func rememberPreference(ctx agent.Context, key string, value any) error {
	return ctx.State().Set(key, value)
}
```

For an event delta, inspect `ctx.Actions().StateDelta` and observe when the
runner persists it.

**Validation:** Run two turns in one session and one turn in a new session.
Which values are visible in each case? Test cancellation and a missing key.

### 14. Split responsibilities across sub-agents

**Concept:** Agent trees, delegation descriptions, transfer boundaries, and
shared session context.

**Learner work:** Write three focused agents:

1. `destination_researcher` — gathers candidate facts;
2. `constraint_checker` — checks traveler requirements;
3. `brief_writer` — produces the final brief.

Attach them through `SubAgents` and give each a narrow description.

```go
root, err := llmagent.New(llmagent.Config{
	Name:        "trip_planner",
	Model:       llm,
	Description: "Coordinates destination research and writes a safe brief.",
	SubAgents:   []agent.Agent{researcher, checker, writer},
})
```

**Validation:** Trace which agent authored each event. Test a request that should
stay at the root and one that should delegate.

**Failure modes:** Duplicate names, vague descriptions, accidental transfer
loops, and sub-agents that can perform actions outside their intended scope.

Sources:

- [Multi-agent concepts](https://google.github.io/adk-docs/agents/multi-agents/)
- [Agent API](https://pkg.go.dev/google.golang.org/adk/v2/agent)
- [Pinned multi-agent examples](https://github.com/google/adk-go/tree/v2.7.1/examples/multiagent)

### 15. Add deterministic workflow agents

**Concept:** Explicit orchestration versus model-chosen delegation.

**Learner work:** Build two versions of the research pipeline:

- sequential: researcher → checker → writer;
- parallel: independent researchers run concurrently, then a writer combines
  their outputs.

Later add a bounded loop for brief revision.

```go
pipeline, err := sequentialagent.New(sequentialagent.Config{
	AgentConfig: agent.Config{
		Name:      "research_pipeline",
		SubAgents: []agent.Agent{researcher, checker, writer},
	},
})
```

Use `parallelagent.Config` and `loopagent.Config{MaxIterations: N}` for the
other experiments.

**Validation:** Record ordering, concurrency, cancellation, and partial
failure. Explain why a fixed workflow is preferable when the order is a
business rule.

**Limits:** The documentation marks template workflow agents as superseded by
graph-based and dynamic workflows. Learn these packages after understanding the
simple agents.

### 22. Package and deploy only after local behavior is understood

**Concept:** Configuration, authentication, persistence, observability, and
operational ownership.

**Learner work:** Containerize the executable only after identifying:

- persistent session, memory, and artifact backends;

- authentication and authorization;
- telemetry and redaction;
- provider/model fallback behavior;
- cost and quota limits.

**Validation:** Document which local guarantees survive deployment and which do

## Evidence boundaries

Keep these claims separate:

- **Documented fact:** An official source describes an API or requirement.
- **Local observation:** This selected model, key, host, and date produced an
  output or error.
- **Design judgment:** The project keeps tools read-only and uses explicit
  confirmation for the fake side-effect experiment.
- **Open question:** A provider/model capability has not yet been tested.

Successful compilation proves package/type compatibility for the selected
module. It does not prove network access, authentication, model behavior,
grounding correctness, race freedom, performance, security, cost control,
production readiness, or learner understanding.
